ECS Pre-Trip Travel Request — Build Specification

A vendor-ready specification of the Pre-Trip Travel Request module: every screen, field, validation rule, program algorithm and configuration switch needed to build it, plus the design decisions that shaped them.

1The Pre-Trip module

The Pre-Trip module captures a travel request before a trip, derives entitlements and the estimated cost, routes it for approval, issues a Travel Authorisation, hands a governed booking instruction to a Travel Management Company (TMC), and seeds the downstream Travel Expense (TE) claim.

Purpose

The module closes the gap between an employee's intent to travel and a booked, policy-compliant, financially authorised trip. It replaces email/spreadsheet approvals and retrospective booking with a single governed flow: capture the trip, derive the entitlement and cost, obtain the right financial authority (DOA), and instruct the TMC — before any spend is committed. It then pre-populates the post-trip expense claim so the claim reconciles to what was approved.

Outcome

Policy enforced before spend

Caps, class entitlement and exceptions are evaluated and routed to the right approver before booking, not discovered at claim time.

Outcome

One Travel Authorisation per trip

A dated, amount-bound TA (TA-YYYY-NNNNNN) is the single source of truth the TMC and the claim both reconcile against.

Outcome

Clean TMC hand-off & claim

A governed, field-filtered booking instruction per traveller; a pre-filled TE claim whose DOA is auto-granted when it matches the estimate.

Capabilities

Request capture

Individual, group (coordinator-raised, multi-traveller, with Excel/CSV bulk upload) and guest (non-employee) requests.

Itinerary & trip types

Round-trip / one-way / multi-city (multi-country), always-on leg builder, personal segments.

Entitlement derivation

Travel class derived from the itinerary (longest-duration leg), per traveller for groups.

Cost estimation

Airfare, accommodation (cap-checked), ODA (rate × eligible days), incidentals; FX conversion; sponsorship.

Policy engine

Common + pre-trip rules → pass / exception / hard stop; hard stops block submission.

Configurable approval routing

RO · Additional · Funding Owner · Cross-BA · Exception · DOA — computed from context + settings.

Charging & allocation

ECS cascade, per-line multi-account splits, auto-allocate by Workday department.

Authorisation & booking

TA issue, validity & booking-deadline tracking, booking-status lifecycle.

TMC hand-off

Governed payload (integration contract), group fan-out (one instruction per traveller), inbound status.

Claim seeding

Pre-populates the TE claim; DOA auto-granted within tolerance.

Amendments & audit

Material-amendment re-approval, immutable version snapshots, field-level audit.

Configuration

Runtime Module Settings drive routing switches, thresholds, caps basis and tolerances.

Scope & boundary

The module extends the existing ECS / ECS-Travel platform. It does not re-implement HR, finance or DOA masters — it reads them. The build team replaces the prototype's mock service layer with real calls to ECS/OutSystems.

Reused (read-only)

ECS reference masters

Employees & appointments, reporting lines, DOA lines, charging accounts (CC/WBS), policy caps & ODA rates, FX rates, workflow amount bands, roles, TMC providers, location master.

New (transactional)

Pre-Trip data store

Travel requests, travellers, itinerary legs, estimated expenses, charging allocations, policy checks, approval steps, bookings, TE claims, audit, attachments.

Integration seam

Mock ECS services

EcsIdentity, EcsCharging, EcsWorkflow, EcsRoles, EcsReference, EcsFx, EcsTravelClassRegister — the interface the vendor wires to live ECS.

On OutSystems, screens map to Screens/Blocks, server actions to Server Actions, the data model to Entities, and the mock services to integration (REST / service actions). 2Core design decisions

These decisions are binding — they shaped the data model, screens and logic below. Deviating from one changes multiple downstream behaviours.

DD-01 · Approval routing is configuration-driven
The route is computed, never hard-coded per user.

An evaluator takes the request context (amount basis, charging department, research flag, exceptions, group flag) and emits an ordered list of approval steps. Decision points are toggled by Module Settings (the existing ECS Configuration mechanism), not by code.

Why: the same engine serves the Travel Request and the TE claim; policy changes are config, not a release.

DD-02 · DOA is always required and traveller-selected
Every request ends at a DOA; the requestor picks the approver.

The DOA step is never dropped. The system offers the eligible DOA candidates (the charging department's DOA line from the amount-band tier upward, excluding travellers) and the requestor chooses — it is not pre-selected. Research routes use the research DOA line.

Why: the DOA holds financial authority; choosing (rather than auto-assigning) records intent and supports delegation.

DD-03 · RO is a configurable decision point
Reporting Officer step = ALWAYS · INDIVIDUAL_ONLY · NEVER.

Default INDIVIDUAL_ONLY: present for an individual request, dropped for a group (the group coordinator raises it). Resolved as the traveller's Reporting Officer; skipped if the RO is a traveller on the request (self-approval guard).

DD-04 · Travel class = derived entitlement, stored; an individual may override with justification
Entitlement is derived & stored; no picker on the trip form; an individual upgrade needs justification and raises an exception.

Class is derived from the itinerary — each flown leg's duration gives its entitled class and the highest wins (the longest-duration leg drives it, critical for multi-city). The derived entitlement is persisted (entitledClassId + classBasis on the request, per traveller for a group, and per leg). There is no class picker on the trip form; an individual request may select a higher class on the Add-Airfare estimate (travelClassId). A chosen class above entitlement: (1) requires a justification — a missing one is a hard stop that blocks submission (CLASS_JUSTIFY); and (2) raises a "Travel class above entitlement" exception (CLASS) that routes to the Exception Approver when exceptionApproverRequired is on, else is surfaced to the DOA. A group books each traveller at their own entitlement (no coordinator upgrade — DD-05).

Why: entitlement is deterministic from the register + itinerary, but a genuine upgrade is allowed with an auditable justification and the right approver — never silently.

DD-05 · Group travel is per-traveller for class & cost; shared for itinerary
One shared itinerary & dates; each traveller at their own entitlement.

Group members share the itinerary and dates (no per-traveller deviation). But travel class is per traveller (each at their own entitled class — the coordinator cannot justify an upgrade on another's behalf), and all costs are per traveller: airfare, ODA and accommodation. An upgrade for one person is handled by removing them from the group and raising a single request.

DD-06 · Accommodation is never shared — each traveller books, pays and claims their own room
No shared/apportioned hotel line.

Accommodation creates one line per traveller (own room, own nights), flowing to that traveller's own TE claim. "Shared — apportion" survives only for genuinely shared incidentals (e.g. a shared taxi under Other), where it is displayed apportioned across the group.

DD-07 · Charging allocation is per-expense-line and fully granular
Each cost line splits across one or more cost centres; lines are already per traveller.

ITEM-mode allocation gives every line a split of {account, %} rows (must total 100%). The request-level allocation that drives routing is the roll-up of net × % over every line × split. An "Auto-allocate by traveller's Workday department" preset fills each line from the attributed traveller's home-department cost centre.

DD-08 · TE claim DOA is auto-granted within a configurable tolerance
No re-approval when the claim matches the approved estimate.

The claim route mirrors the request (Verifier → Exception? → RO? → DOA). The DOA step is auto-granted from the approved Travel Request when the claim is within the configured tolerance (% and absolute SGD), adds no new expense type, introduces no new policy exception, and keeps the same charging department. No new expense type can be added at the claim. A changed charging account breaks the auto-grant and routes to the DOA of the new account (not the original). The tolerance threshold itself is an open item (§16, O-1).

DD-09 · One always-on itinerary; trip type is a preset, not a mode
Round-trip / One-way / Multi-city reshape the same leg builder.

The leg table is always shown. Trip type presets it: Round-trip = Outbound + mirrored Return, One-way = one leg, Multi-city = user-determined (add / reorder / remove). A round-trip may carry a personal segment. Main destination (for ODA defaults) = longest-stay leg. The preset legs track the official dates — Outbound ← official start, Return ← official end — so a later change to an official date moves a mirrored leg, while a leg the traveller set to a different date is preserved (applied on the form and re-asserted on save).

DD-10 · Booking arrangement and TMC booking method are separate
What arranges the trip vs how the TMC fulfils it.

Booking arrangement: Auto (route by policy to a TMC) · a specific TMC provider · Self-booked · Host-arranged · No booking. TMC booking method (TMC channel: online / agent-assisted / offline) applies only when arranged via a TMC. The resolved TMC is shown read-only on the trip form.

DD-11 · The airport master is the TMC's booking source
One IATA location master, shared.

From/To on every leg read the shared ECS Location master (IATA airports). Each leg's code is carried verbatim into the TMC booking instruction. In production this master is synced from the TMC/GDS airport feed.

DD-12 · A Travel Request has no "Reject"
Dissent = Send Back.

An approver who disagrees sends the request back (→ Sent Back → Draft) to be revised and resubmitted. There is no terminal reject on the request. (The TE claim keeps standard claim controls.)

DD-13 · Group travel is employees-only (max 10); guests use a separate request
No employee + guest mixing initially; a group is employees only, capped at the TMC group limit.

Per the CFO review, a group request carries employees only, up to groupMaxTravellers (default 10, the TMC group-fare limit). Guests are not mixed into a group — a non-employee is raised on the standalone Guest request (one guest per booking), where guest cost is host-settled by TMC direct-billing (ECS stores name/email/org only — DD-23). The mix capability remains behind groupGuestMixAllowed but is default off. Student group travel is out of scope for now (§16). Full logic in §14.

Why: a group spans multiple ROs and shared logistics, so employees-only keeps charging, settlement and routing clean; guest cost has a single host-settled path handled on the guest request. Mixing can be revisited later via the setting.

DD-14 · One live authorisation per trip — a duplicate is blocked, not silently doubled
A traveller can't be on two trips at once; a re-raise must cancel/amend the original first.

A request may not be submitted when a live request (Submitted · Pending* · Approved · Amendment In Progress) already shares a traveller and overlaps the official dates. Same destination = a true duplicate → hard block (submit disabled; the traveller cancels or amends the original first); a different destination with overlapping dates = a date clash → warning (possible double-booking). Groups match per shared employee; guests are excluded (a guest may legitimately appear on more than one host's trip). The conflict is surfaced upfront — the same banner appears on every editable step (Trip · Estimates · Charging · Policy Review) as soon as the official dates are known, so the traveller is warned early rather than discovering it only at the Submit gate; the hard block at submission stays the backstop.

Why: after a failed booking a traveller tends to re-raise; without this guard two live Travel Authorisations can exist for one trip (double-booking, double-spend, orphaned TA). The guard makes "cancel/amend before re-raise" enforceable, and surfacing it from the Trip step saves the traveller from completing a request that cannot be submitted.

DD-15 · A failed booking recovers by amend-and-reroute or cancel-and-reraise; the OBT reports status, it does not reject
The OBT/TMC is a fulfilment channel, not an approver — "failed" is inferred from not-issued within the booking window.

The OBT (e.g. Cytric, Trip.Biz) returns booking status (confirmed / issued / changed / cancelled / refunded), not an approval verdict. A booking that does not issue within the window is Booking Failed. Recovery offers, gated by the booking window (deadline / TA validity): re-send (retry as-is), amend & re-route (reopen to Amendment In Progress, re-derive the route — the single-TA path), or cancel & re-raise (the original goes terminal, freeing the overlap for a fresh request under DD-14). A material booking deviation (fare over tolerance) likewise routes to re-approval — it is never the OBT "sending the request back".

Why: the fare/seat may not survive an approval round-trip, so recovery must consider the window; and authority stays with the human approver, never the booking tool.

DD-16 · Estimate inputs default to the policy figure, and are scoped to entitlement
Accommodation rate defaults to the city's cap (editable); ODA auto-computes; a guest estimate is airfare + accommodation only.

An estimate pre-fills from the governing policy figure so the common case needs no lookup: the accommodation quoted rate defaults to the selected city's hotel cap and follows a city change, but stays editable for an actual quote; ODA auto-computes from the policy rate × eligible days over the official range. Entitlement scopes what can be added: for a guest the ODA form is disabled (not a guest entitlement — §8), so a guest estimate is airfare + accommodation only; in a group the ODA traveller picker offers employees only.

Why: defaulting to the cap removes a manual lookup and anchors estimates to policy, while keeping the quote editable; scoping stops a guest accruing a cost with no settlement path.

The decisions below were added or confirmed at the CFO review and are being incorporated; see §17 for status.

DD-17 · One Travel Request → one Expense Claim → many PNRs; the TMC is queried BY the Travel Authorisation
A trip may hold multiple PNRs (a TMC splits a multi-city itinerary for competitive fares); retrieval is keyed by the TA, not the PNR.

ECS's one-PNR-per-claim assumption is replaced: a request/claim may reconcile N bookings, one per PNR, with each PNR mapped to its legs, the deviation check on the aggregate airfare, and the claim aggregating across PNRs. The claim still links one Travel Request → one claim; it is the booking layer beneath that goes 1→N. With the pre-trip module inside ECS the claimant creates the claim FROM the Travel Request (not by selecting a PNR), so the TMC exposes booking retrieval BY the Travel Authorisation number — a "bookings for TA-YYYY-NNNNNN" call that returns the full set of PNRs under that TA. The PNR stays the TMC's native record id; the TA is the query/correlation key. The feed is push-primary (bookings arrive against the TA, so the claim pre-populates with zero PNR entry) with a pull-by-TA refresh fallback for the freshest actuals; the retrieval captures the PNR set + booked fares + booked dates (including the booked arrival dates). The PNR(s) are shown as provenance on the Travel Request — a TR-level "Booking reference(s)" summary (count + each PNR/ticket/status/fare) plus a per-leg PNR tag on the itinerary (segment↔leg matched by origin/destination and date; a hotel is shown at the stay level, a self-booked leg shows no PNR, and a booking whose segments don't line up degrades to the TR-level summary rather than mis-tagging). Built in the prototype.

Why: competitive multi-city fares are routinely ticketed as separate PNRs; forcing one PNR per claim loses fares and mis-reconciles. Keying retrieval by the TA (not the PNR) returns every PNR in one call — so the claimant never hunts PNRs and none is missed — ties the actuals to the governed authority the DD-08 auto-grant reconciles against, and survives a re-issue (a new PNR/ticket under the same TA is picked up automatically). (Resolves the former OD-01.)

DD-18 · Online hand-off only for deterministic itineraries; variations go agent-assisted/offline
Straight-through TMC transmission needs a clear, deterministic instruction.

An itinerary that is clean and unambiguous is sent online (straight-through); one with variations — per-traveller different dates, personal extensions, complex multi-city — is routed agent-assisted / offline, where an agent handles what cannot be passed as a deterministic instruction. This applies to groups whose members travel on differing dates.

Why: a non-deterministic instruction booked straight-through mis-books; the offline channel exists precisely for these.

DD-19 · Settlement channel — airfare is always CTA; hotel is a requestor choice; reimbursable = employee-settled only
CTA (Central Travel Account) is a payment channel, not a group-hotel feature. Airfare is central; hotel is CTA-or-individual by choice; ODA is always claimed.

Settlement decides who fronts the money, and therefore whether a cost line is reimbursable to the employee or reference-only in the claim. It is separate from authorisation and cost ownership (the approval amount still covers the full committed spend, and the CC/WBS charging allocation is unchanged — CTA is only the payment channel). Airfare is CTA / central-billed whenever the trip is a TMC arrangement (reference-only in the claim, never reimbursed; a self-booked flight is employee-paid → reimbursable). Hotel is a requestor choice per trip — CTA (central-billed, reference-only) or Individual (employee pays & claims) — the single toggle applies to every hotel line and to individual and group bookings alike; CTA is offered only when the trip is a TMC arrangement (a self-arranged room cannot be central-billed). ODA / other are always employee-settled. The booking instruction carries a per-hotel-segment billTo = CTA | TRAVELLER, and the claim treats central lines (TMC airfare, CTA hotel) as Reference (shown for comparison, not reimbursed) and employee lines as Editable. A single settlement helper is the one source of truth for this, so the DD-08 auto-grant tolerance compares the reimbursable (employee-settled) portion on both the claim and the approved baseline. The airfareTreatment setting now only governs how a central airfare line posts (direct-to-SAP vs shown-in-claim), not whether it is reimbursable. Built in the prototype. (This supersedes the former group-hotel-block-only CTA scope.)

Why: whoever did not front the cost cannot be reimbursed it, or it double-pays; making settlement a per-line fact (airfare central, hotel by choice, ODA claimed) keeps the claim reimbursing exactly the employee-paid portion while still showing the full trip cost for reconciliation.

DD-20 · Approved upgrade cost is split: base vs upgrade differential
Base entitlement and the upgrade differential charge to different accounts.

Where an approved class upgrade is permitted, the cost splits: the base entitlement portion → the normal operating / project account; the upgrade differential → a designated reserve (M6) account. A configurable allocation rule (a Finance-set proxy % per upgrade scenario) governs the split, and the resulting allocation is passed to the TMC so the finance interface preserves it. The exact percentages are open (§16, O-5).

Why: an upgrade differential is funded differently from the entitled fare; the split must survive into the financial posting.

DD-21 · Guest travel-document data is collected by the TMC, not ECS (PDPA)
ECS stores name / email / organisation only; the TMC collects passport & profile.

ECS captures basic guest data only — name, email, organisation / host. It does not store passport or travel-document details. The booking instruction directs the TMC to send the guest a separate link to collect passport and traveller-profile data directly, limiting ECS's hold of sensitive personal data (PDPA).

Why: minimise sensitive-data capture in ECS; the TMC already runs a compliant profile-collection flow.

DD-22 · Cancellation is local before hand-off, TMC-mediated after
Once transmitted/booked, cancellation goes through the TMC — not a local ECS cancel.

Before hand-off: the traveller withdraws/cancels in ECS. After the request is transmitted or booked: cancellation must go through the TMC (a ticket may be issued or cost incurred); the TMC feeds the cancelled / not-booked status back to ECS. This, with the duplicate guard (DD-14), prevents a double-booking when the traveller later raises another request.

Why: a local cancel after ticketing desyncs ECS from a live booking and risks double spend.

DD-23 · Emergency pre-trip — book first, raise later
One emergency lane: on a named officer's authorisation, book first; the full approval workflow still runs, ratified retrospectively.

A single bounded, audited emergency lane — book first, raise/approve later. It changes the timing of approval, not who approves: on a named authorising officer's authorisation (recorded, with the authorising e-mail attached as mandatory evidence, and never the traveller themselves), the trip may be booked (or already booked) before approval completes, but the full approval route still runs and is ratified retrospectively — RO / Additional / Exception / cross-charge / DOA as applicable, no step skipped. Guard rails: the lane is soft-gated by a configurable lead-time window (emergencyLeadDays, default 14 days to the earliest departure) — within the window it is freely available; outside it (ample runway) a detailed justification and an explicit confirmation are required and the request is flagged Outside standard window for the approver and in reporting. It is offered only for agent-assisted / offline TMC bookings (a human agent holds/places the booking ahead of approval — DD-18), a destination is mandatory (DD-27), and policy hard-stops still apply. The request is flagged E (Emergency) on the dashboard and auto-handed to the TMC on submit (DD-26), carrying an EMERGENCY_BOOK_FIRST indicator so the TMC reconciles to any space already held and does not double-book. Built in the prototype.

Why: real emergencies can't wait for a full pre-trip cycle, but an emergency should buy time, not a lighter approval — so the controlled lane keeps the full governance (named authoriser + e-mail, justification, lead-time gate, retrospective ratification of the whole route, audit) while letting the trip be booked. (Resolves the former OD-02.)

DD-24 · Approvals live in the ECS dashboard; the approver sees a one-page summary
Tabs in the existing ECS approval dashboard, not a separate portal; policy exceptions emphasised.

Travel-request approvals are surfaced as tabs (Travel Requests / Expense Claims) in the existing ECS approval dashboard, not a standalone portal. The approval page is a one-page at-a-glance summary — purpose, dates, cost, charging and policy exceptions visible without extensive scrolling — with policy exceptions given stronger visual emphasis.

Built in the prototype (E9): the RO/DOA dashboard has live Travel Requests / Expense Claims tabs, each with its own pending counter for the acting approver; rows carrying a policy exception are shaded and flagged; “Review →” opens the one-page Approval Summary (traveller & purpose, trip, cost & charging, travel arrangement, policy exceptions, and an explicit “You are approving” statement), with the full detail cards on a separate Full Details page. The Trip Details tile shows the trip type (one-way / round trip / multi-city with stop count) and, for a multi-city trip, the ordered city route (e.g. SIN → TYO → OSA → SIN) with a country count; a group booking shows its traveller count. The Travel Request Dashboard is traveller-scoped (administrators see all) with search / type / status filters and a request-type flag S (Standard) / E (Emergency, DD-23).

Why: approvers already live in the ECS dashboard; a single consistent surface and a scannable summary speed decisions and reduce missed exceptions.

DD-25 · A guest may be upgraded above Economy only with justification and Provost approval
Guest travel class is Economy by default but editable; a higher class needs a justification and the host school's Provost approves.

A guest defaults to Economy (no entitlement profile), but the class is editable: choosing a higher class requires a justification (hard-stop if missing) and raises a guest-upgrade exception that routes to the Provost of the host school — not the generic Exception Approver. The per-school Provost list is a maintainable reference master, surfaced for selection when a guest upgrade is requested; the approved class and the exception then flow to the TMC. (Refines the guest-Economy default of DD-16 / §14.)

Why: an invited guest (e.g. a senior speaker) may warrant a premium cabin, but authorising that spend sits above the host department — with the Provost — so the upgrade is governed, not silent.

DD-26 · The TMC hand-off is automatic — Travel Admin does not trigger it
Emergency: sent on submit. Standard: sent on final approval. Manual send is a fallback only.

The governed booking instruction is transmitted automatically, with no manual step: a standard request is handed off on final approval (immediately after the Travel Authorisation is issued), for TMC-arranged bookings only; an emergency request is handed off on submit, ahead of the retrospective approval (DD-23). The send is idempotent — a booking already sent / in-flight / booked is never re-transmitted, so a re-submit or re-approval cannot double-book. The manual “Send to TMC” control is retained only as a fallback (e.g. to re-send after a failed hand-off); the failure path (Failed → re-send) stays manual so a failed auto-send surfaces rather than silently looping.

Why: a human trigger is an avoidable delay and a point of inconsistency; firing the hand-off on the approval/submit event — with idempotency — makes it reliable while keeping a manual lever for recovery.

DD-27 · A destination is mandatory on every travel request
No request is submitted without a destination — the approver, policy engine and TMC all key off it.

Every request must carry a structured destination (destCity + destCountry, derived from the itinerary's main leg). Submission is blocked in all lanes, including emergency, when no destination has been captured — a free-text justification note is not a destination. The one-page Approval Summary degrades a missing value to “Not specified” rather than a broken field, but the submit guard prevents that state from reaching an approver.

Why: the destination drives entitlement, ODA, policy caps, risk assessment and the booking instruction; a request without one cannot be assessed or booked.

DD-28 · Separation of duties — an approver never originates, nor approves, its own request
Approver-only roles cannot raise a travel request; and no one approves a request they are travelling on or raised.

Maker and checker are kept apart on two layers. Creation (who may raise): only a persona with a creation remit sees and can use Create Travel Request — the traveller (for themselves), a delegate (for their principals), a PA / Travel Requestor (for their department), or the Travel Administrator (agent-assisted, on behalf of any traveller — §8.3). An approver-only persona — DOA, Research DOA, Exception Approver, and likewise System Administrator and Finance (read-only) — has no creation remit: the nav item is hidden, the create page returns a “No authority to raise a travel request” notice, and the server actions (individual / guest / group) reject the attempt — so a DOA cannot raise a request it would later approve. Approval (who may decide): a self-approval set of every traveller on the request plus the requestor who raised it is applied to every route step; a dual-role officer (e.g. an RO who is also the traveller, or a delegate who also holds DOA authority) is routed past their own step — the RO step escalates up the reporting line, the DOA step escalates up the department DOA tier line, and the cross-BA / Exception steps pick the next eligible approver — each flagged “escalated — self-approval prevention” in the route and audit. Built in the prototype.

Why: letting an approver both raise and approve (or sit on the route of) a request collapses the maker/checker control the whole module rests on; gating creation by remit removes the common case, and the route-level self-approval set is the backstop for anyone who legitimately raises a request but also holds authority on it.

DD-29 · Policy-driven estimates (ODA & accommodation) are auto-derived per city from the itinerary
The system computes the ODA and hotel lines for the traveller — one per city — from the itinerary; airfare stays traveller-entered; nothing is fed from the TMC.

The two policy-driven cost lines are generated automatically from the trip, one per overnight city (derived from the itinerary leg dates, so the stay/day counts are reliable), rather than hand-keyed. Accommodation — one line per stop at the city cap as the default nightly rate; the rate is editable by the traveller/requestor while the stay (nights/dates) is locked to the itinerary. A rate above the cap is budgeted at the cap (the excess is a cap variance) and requires a justification — a hard stop (HOTEL_JUSTIFY) blocks submission otherwise, mirroring the class-upgrade rule (DD-04). ODA — one line per city at that country's daily rate, read-only (a policy figure, not edited), with the ECS duration tiers: days 1–15 at 100%, days 16–31 at 75%, and days 32+ at the country's monthly allowance rate pro-rated per day (÷ 30) — so a short trip is at the full daily rate and only a long-term trip steps down. ODA is an employee entitlement only (guests get none). The lines re-derive whenever the dates or stops change (which resets an edited hotel rate back to the cap); airfare remains a traveller-entered quote. The one-page breakdown presents each line as two labelled groups (Stay · Rate / Trip · Rate) with the budget basis in plain words (“actual quote, under cap” / “capped at the city cap”). Built in the prototype.

Why: ODA and hotel are policy figures the system can derive, so making the traveller re-key them is error-prone and off-policy; auto-deriving per city keeps multi-country trips correct, the duration tiers match the ECS ODA configuration, and mandating a justification for an above-cap hotel keeps every exception accountable.

DD-30 · CTA-settled charges — clearing-account master, claim reference lines, and a reconciliation listing
ECS's posting programme posts the central (CTA) charges; ECS adds the CTA→clearing mapping it lacks, shows the charges on the claim as reference (not reimbursed), and lists them for finance to reconcile.

Charges paid centrally on a Central Travel Account (CTA) — TMC-booked airfare and a CTA-settled hotel (DD-19) — are posted to the GL by ECS's existing posting programme; the one thing it cannot derive is the clearing account for a given CTA. So ECS holds a small CTA master: a posting-only lookup keyed by the ctaAccountId the card / TMC feed reports on each charge (never derived by ECS), mapping it to its clearing GL account — different CTA accounts map to different clearing accounts. On the TE claim, CTA-settled lines auto-populate as Reference (shown for the full cost picture, not reimbursed, locked) and are deducted from the Total Reimbursable Amount (consistent with the DD-08 reimbursable scope). A read-only CTA Charges listing groups the captured CTA charges by clearing account (with CSV export) as a one-sided view for finance to reconcile against the provider statement outside ECS — ECS performs no matching or posting there. Guest bookings are CTA-settled too — airfare and accommodation are paid centrally and their charges are captured and listed for reconciliation, but a guest files no TE claim (DD-21), so guest charges are never reconciled through a claim. Guest charges may lodge to the same CTA account as employees or to a separate guest CTA account — the account is feed-reported, so the master simply holds whichever the TMC uses. Built in the prototype.

Why: the posting programme already handles the GL posting, but it needs the clearing account per CTA; keeping that mapping, the claim's reference treatment and the reconciliation listing inside ECS keeps the finance logic governed and auditable without duplicating the posting or coupling it to the TMC.

7Program logic — approval routing

The route builder consumes the request + settings and emits ordered steps. Order: Additional → RO → Funding Owner → Cross-BA concurrence → Exception → DOA.

function buildRoute(req, settings):
  steps = []; travellers = req.isGroup ? req.travellers : [req.travellerId]
  dept = highestChargingDept(req)          # department bearing the largest %
  research = isResearch(req) and not settings.sameRouteResearch

  # 1 · Additional Approver (traveller-chosen, optional) — self-approval guard
  if req.additionalApproverId and notTraveller:
     steps += ADDITIONAL(req.additionalApproverId)

  # 2 · RO decision point (DD-03)
  roNeeded = settings.roRequirement == "ALWAYS"
          or (settings.roRequirement == "INDIVIDUAL_ONLY" and not req.isGroup)
  if roNeeded and RO(traveller) notTraveller: steps += RO

  # 3 · Funding Owner (cross-charge requiring owner concurrence)
  if anyAllocation.crossCharge and fundingOwner: steps += FUNDING_OWNER

  # 4 · Cross-business-area concurrence (§18)
  for each non-primary BA whose share > settings.crossBaThresholdSgd:
     steps += FUNDING_OWNER(thatBA)            # skip duplicates / travellers

  # 5 · Exception approver — only if a policy exception exists AND configured on
  if hasException and settings.exceptionApproverRequired: steps += EXCEPTION

  # 6 · DOA (always) — tier from the amount band, line per research route (DD-02)
  band = bandForAmount(approvalAmount)
  doaId = req.selectedDoaId   # traveller-chosen; else pickDoa(line, band.tier, escalate past travellers)
  steps += (research ? RESEARCH_DOA : DOA)(doaId)
  return steps

DOA candidate derivation (what the requestor chooses from)

function doaCandidatesFor(req, approvalAmount):
  line = research ? dept.researchDoaLine : dept.doaLine
  band = bandForAmount(approvalAmount)
  tier = min(band.doaTierIndex, line.length-1)
  return line.slice(tier)                    # required tier upward (higher authority can also approve)
         .filter(id not in travellers)          # never a traveller (self-approval, §13.5)
Status derivation. The request's Pending * status is set from the first pending step's role (RO → Pending RO Approval, Additional → Pending Additional, Exception → Pending Exception, else Pending DOA).

8Program logic — travel class entitlement

Entitlement is derived from the Travel Class Register (per-employee policy group, entitled class, minimum flight-hours threshold, effective dates) across the whole itinerary.

function entitledForDuration(employee, hours, onDate):
  entry = register(employee, onDate)
  return entry and hours >= entry.minHours ? entry.entitledClassId : ECONOMY

function entitledForItinerary(employee, legs, onDate):   # DD-04
  perLeg = [ entitledForDuration(employee, leg.durationHours, onDate)
             for leg in legs if not leg.isPersonal ]
  return highest-rank(perLeg)                 # longest-duration leg drives the class
  • Individual: the derived entitlement is stored (entitledClassId + classBasis); the chosen class (travelClassId) defaults to it but may be overridden to a higher class on the Add-Airfare estimate.
  • Group (DD-05): compute per traveller and store on each TravelRequestTraveller.chosenClassId / entitledClassId. Each airfare line is stamped with that traveller's class; lines re-sync if the itinerary changes. No coordinator upgrade.
  • Leg duration is derived server-side from the destination city's flight-hours — not trusted from the form.

Upgrade control (chosen > entitled)

if rank(chosen) > rank(entitled):                 # per traveller
  raise EXCEPTION "Travel class above entitlement"   # code CLASS
  if not justification:
     raise HARD_STOP "Class upgrade justification required"  # code CLASS_JUSTIFY — blocks submit
# the CLASS exception then routes to the Exception Approver when exceptionApproverRequired,
# otherwise it is surfaced to the DOA (§7 routing, DD-01).
So an individual may fly above entitlement, but only with a stored justification (absent = hard stop) and the right approver — the Exception Approver or the DOA per exceptionApproverRequired. Nothing is silent; the derived entitlement is always retained for comparison.

function resolveItem(lines):
  charges = []
  for line in lines:
     allocs = line.allocJson or [{code: line.mainAccount, pct: 100}]
     line.save(allocJson = allocs.length>1 ? allocs : null)   # persist genuine splits
     for a in allocs: charges += {code: a.code, net: line.net * a.pct/100}
  rows = rollupByCode(charges)         # sum net per account → % of total
  persist ChargingAllocation(rows)        # drives routing — unchanged contract

Auto-allocate by traveller's Workday department (DD-07)

function deptAllocsFor(line):
  shares = line.isShared
         ? (line.shareMap or equalSplit(req.travellers))   # shared incidental
         : [{ eid: line.travellerId, pct: 100 }]              # per-traveller line
  byCode = {}
  for s in shares:
     cc = employee(s.eid).defaultChargingCode                # Workday home-dept cost object
     byCode[cc] += s.pct                                      # aggregate same-dept travellers

10Program logic — TE claim & DOA auto-grant

The claim route reuses the same configurable rules; the DOA step is auto-granted when the claim matches the approved request.

function doaAutoGrant(claim, req, settings):   # DD-08
  if req.status not in [Approved, Closed]:  return false  "not approved"
  if not req.authorisationNo:               return false  "no TA"
  over = claimTotal(claim) - approvedAmount(req)
  withinTol = over <= settings.teAutoGrantToleranceAbsSgd
          and over <= approvedAmount * settings.teAutoGrantTolerancePct/100
  if not withinTol:                         return false  "beyond tolerance"
  if claimHasNewExpenseType(claim, req):   return false  "new expense type"
  if claimHasNewException(claim, req):     return false  "new exception"
  if claimChargingDept != reqChargingDept:  return false  "DOA changed"
  return true  # DOA step marked Approved · autoGranted, cites the TA

New exception = over the approved amount beyond tolerance or any line claimed without a receipt. The Verifier (Travel Administrator) is always first; the Exception and RO steps follow the same config as the request.

12TMC integration

The hand-off is automatic (DD-26) — on submit for an emergency (book-first), on final approval otherwise. At that point a governed booking instruction is assembled from the request, filtered by the admin Integration Contract (per-field include/treatment flags); the send is idempotent, so a booking already sent / in-flight / booked is never re-transmitted.

Hand-off payload (per instruction)

  • Authorisation & traveller (or guest) identity; booking method; booking deadline; approval validity.
  • Air segments — origin / destination (IATA, verbatim), depart date, approved class. Hotel segments — city, nights, capped nightly.
  • Approved cost ceiling; approved exceptions; charging (primary bears the airfare posting); approval metadata.
  • Group fan-out (§9.3): one approval → one instruction per traveller, each carrying that traveller's own class, nights and cost share.
  • Guest (§8): a guest instruction carries bookingFor = GUEST, the guest identity, Economy class, and settlement = HOST_DIRECT_BILL with the host cost object.
Booking arrangement decides the channel: AUTO routes to a TMC by policy/destination; a provider id targets a specific TMC; Self-booked / Host-arranged / No booking skip the hand-off. The resolved TMC is shown read-only on the trip form and the review/detail pages.

Inbound outcomes & failed-booking recovery (DD-15)

The OBT/TMC (e.g. Cytric, Trip.Biz) is a fulfilment channel, not an approver: it returns booking status — confirmed / issued / changed / cancelled / refunded — never an approval verdict. ECS normalises these into its own booking-status lifecycle (§4); "failed" is inferred from not-issued within the booking window, not assumed to be a single push event. A material booking deviation (fare over tolerance) raises a BookingDeviation(action=Reapproval) — again a deviation loop, not the OBT "sending the request back".

On Booking Failed the booking page shows a recovery panel, gated by the booking window (booking deadline / TA validity — a closed window means a re-send is unlikely to help):

RecoveryEffect
Re-send to TMCretry the same instruction (fare/seat may have returned)
Amend & re-routereopen to Amendment In Progress, re-derive the approval route, edit the itinerary — keeps a single TA lineage
Cancel & re-raisethe original goes terminal (Cancelled); a fresh request is then allowed under the duplicate guard (DD-14)
For an urgent trip the TMC typically books offline and contacts the traveller directly; once a replacement is booked, the original is cancelled so no two authorisations stay live — the duplicate guard (DD-14) blocks a re-raise until the original is cancelled or amended.

Downstream handling

  • Entitlement (§8): a guest short-circuits to Economy; employees derive per itinerary. Each member's class is stamped on their own airfare line.
  • Charging (§9): a guest's cost maps to the host department's cost object; the per-department roll-up still derives the DOA from the highest-share department. Guest cost is never split onto the guest.
  • No shared slice, no ODA: shared incidentals split across employee members only, and ODA is blocked for guests at authoring. Both are validated at submit — a shared line that names a guest, or a guest ODA line, is a hard block. (A guest's only settlement path is direct-billing, which covers neither.)
  • Review & detail: the roster shows each member with a Guest pill, their org (Guest · MIT), and Economy class.
  • TMC fan-out (§12): a guest instruction carries bookingFor = GUEST, the guest identity block, Economy class, and settlement = HOST_DIRECT_BILL with the host cost object.
  • Claim: claims are keyed to the logged-in persona, so a guest — having no login — can never produce one; the host absorbs guest cost.

Guest settlement — host direct-billed

Because a guest files no claim, their cost is not reconciled through the claim pipeline. It is host-settled: the TMC direct-bills the host department cost object, and the actual is read from the guest's own booking in the group fan-out. The group detail page carries a Guest Settlement card:
